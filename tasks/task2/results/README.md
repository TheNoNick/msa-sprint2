# Задание 2. booking-service и booking-history-service

## Что сделано

- **`booking-service`** — сервис бронирований на gRPC по `booking.proto`. Логика перенесена из монолита один в один, данные о пользователях, отелях, отзывах и промокодах берутся из монолита по REST. Своя база `booking-db`.
- **Монолит переключён на новый сервис** через переменные `BOOKING_SERVICE_EXTERNAL_HOST` и `BOOKING_SERVICE_EXTERNAL_PORT`. 
- **События в Kafka.** После создания бронирования публикуется `BookingCreated` через outbox: бронирование и событие пишутся одной транзакцией, поэтому события не теряются, даже если Kafka недоступна.
- **`booking-history-service`** читает события и считает статистику в своей базе `history-db`, боевые базы не трогает. API: `/api/history`, `/api/stats/users`, `/api/stats/hotels`, `/api/stats/days`.
- **Тесты** доработаны: бронирования грузятся в `booking-db`, убран запрос всех бронирований без `userId`, добавлена проверка, что событие дошло до истории.


## Стратегия миграции данных при запуске нового сервиса

Таблицу `booking` пишет только модуль бронирования, а сами бронирования только добавляются: изменения и отмены в коде нет. Поэтому двойная запись не нужна, хватает одного переключения:

1. **Подготовка.** Поднимаем `booking-service` с пустой базой. Схема `booking` совпадает со схемой монолита, поэтому данные переносятся без преобразований.
2. **Первичное копирование.** Копируем `booking` из базы монолита в `booking-db` с теми же `id` и запоминаем максимальный `id`. Sequence в новой базе стартуем с запасом (`max(id) + 1 000 000`), чтобы новые `id` не пересеклись со старыми при откате. Старым записям без `created_at` ставим дату миграции: прокси монолита не разбирает пустую дату.
3. **Переключение.** В тихое время докопируем записи с `id` больше запомненного, выставляем `BOOKING_SERVICE_EXTERNAL_HOST` и перезапускаем монолит. С этого момента и запись, и чтение идут в `booking-service`, и таблица монолита больше не меняется (видно в `bookings-select.txt`).
4. **Сверка.** Сравниваем количество записей и контрольные суммы в обеих базах и прогоняем регресс-тесты.
5. **Откат.** Убираем переменную и перезапускаем монолит. Чтобы не потерять бронирования, созданные после переключения, их дописываем обратно в таблицу монолита (например, по событиям `BookingCreated`).
6. **Вывод.** Когда всё стабильно, таблица в монолите становится архивом, а потом удаляется вместе с кодом бронирования.

`booking-history-service` получает только новые бронирования. Если аналитикам нужна история до миграции, её можно один раз догрузить из `booking-db` тем же форматом событий.

## Что сохранили ради совместимости

- Скидка по-прежнему вычитается из цены как сумма, а не как процент: 100 − 10 = 90. Так работал монолит, и тесты это проверяют.
- Любой отказ в бронировании монолит отдаёт как HTTP 500, как и раньше. `booking-service` возвращает понятный gRPC-статус `FAILED_PRECONDITION` с причиной, но прокси превращает его в 500.
- Прокси возвращает `promoCode: ""` вместо `null`, если промокода нет: в gRPC у строки нет `null`.
